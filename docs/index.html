01 / INTRODUCTION

Professional Self-Assessment

Professional Self-Assessment

I started my Computer Science degree with years of experience working with unmanned aircraft, systems integration, flight testing, and technical instruction. That background gave me a practical understanding of what happens when software does not behave as expected. Completing the program helped me connect that experience to the engineering work behind the systems I use. I now approach software with the same focus on repeatability, verification, and clear communication that I brought to flight operations.

Collaboration and Communication

In aviation and systems testing, a good technical solution is only useful if the people operating, testing, and maintaining it understand the decision. I have worked across flight crews, engineering teams, and leadership, translating technical limitations into test priorities and actionable plans. My coursework reinforced the value of documenting design choices, explaining trade-offs, reviewing code, and communicating results to both technical and nontechnical audiences. The code review video and written narratives in this portfolio demonstrate that approach.

Engineering, Algorithms, and Data

My Software Engineering concentration strengthened my understanding of object-oriented design, separation of concerns, testing, and maintainable architecture. For the capstone, I revisited a CS-320 Java application and replaced three isolated service implementations with a common repository contract and shared validation. I added case-insensitive searching, filtering, and sorting without discarding the HashMap that already handled direct ID lookups efficiently. I then introduced SQLite persistence through JDBC repositories. Working through these enhancements taught me that good engineering is not about adding the most complicated solution; it is about selecting an approach that solves a real problem and can be explained, tested, and maintained.

Security and Quality

Security and reliability are connected to design decisions. I used prepared SQL statements to keep data separate from query text, database constraints to reinforce validation, and resource-management patterns to close connections and statements safely. Defensive copies and immutable result lists also help limit unintended modification. Beyond the capstone, my experience with software test automation and systems verification has emphasized regression testing, traceability, and reproducible results. The final capstone runners reported 23 of 23 algorithm checks and 17 of 17 SQLite integration checks passing; these are standalone checks rather than JUnit test counts.

Professional Direction

My long-term goal is to continue developing as a software engineer, with an emphasis on test automation, systems integration, and software quality. The capstone brings together skills from software engineering, data structures, databases, security, and technical communication in one evolving artifact. The original application establishes the baseline; the three enhancements show how I evaluate existing code, make deliberate design decisions, and verify improvements. This portfolio is a record of that growth and an example of the kind of disciplined, practical engineering I want to keep doing.

01

Software Design & Engineering

Generic repositories, constructor injection, shared validation, defensive copies, and clearer responsibilities.

Read the enhancement narrative ＋

Artifact and Rationale

This enhancement builds on the Contact, Task, and Appointment services originally developed for CS-320 Software Testing, Automation, and Quality Assurance. I chose it because the original services demonstrated validation and testing, but their duplicated logic made future changes more difficult. The capstone was an opportunity to improve the architecture while preserving the original behavior.

Enhancement and Skills

I introduced a generic Repository<T> contract, an InMemoryRepository implementation, an Identifiable interface, shared validation, consistent exception handling, defensive copies, and unmodifiable result collections. Constructor dependency injection lets each service accept a repository without knowing how records are stored. That separation means an in-memory repository can be replaced with a SQLite-backed implementation without rewriting the service methods. It also makes isolated testing easier and keeps persistence decisions out of the business logic.

Evidence and Reflection

The Java service classes and repository implementations provide the architectural evidence. The 23-check algorithms runner exercises selected service behavior after refactoring, and the 17-check SQLite runner verifies the alternate persistence implementation. Both suites passed in the final local run. These results are useful regression evidence but do not establish that every original CS-320 JUnit test was rerun. The main lesson was that improving a system can mean removing duplication and reducing coupling instead of adding visible features.

Course Outcomes

This enhancement contributes to Outcome 3 through design trade-offs and separation of responsibilities, Outcome 4 through reusable Java architecture, and Outcome 5 through defensive handling and validation. The accompanying code review and explanations also contribute to Outcomes 1 and 2 by making the decisions accessible to reviewers and stakeholders.

02

Algorithms & Data Structures

Case-insensitive searching, sorting with Comparators, upcoming-appointment filtering, and explicit Big-O trade-offs.

Read the enhancement narrative ＋

Artifact and Rationale

The second enhancement expands the same Java Contact, Task, and Appointment application with practical searching, filtering, and sorting. I kept the existing HashMap-based repository because exact-ID lookup was already efficient and did not need to be replaced just to introduce a different data structure.

Algorithms and Complexity

Exact ID lookup in an in-memory HashMap is O(1) on average, with O(n) worst-case behavior under pathological collisions. Case-insensitive contact and task searches scan the records in O(n) record comparisons, excluding the additional cost of string matching. Filtering n appointments and sorting k qualifying records takes O(n + k log k) worst-case time; sorting all n records takes O(n log n) worst-case time. Search results require O(k) space, and copied sorted lists require O(n) space. A linear scan roughly doubles its record comparisons when the record count doubles, whereas sorting grows faster. Java Comparators keep the code clear and avoid unnecessary custom sorting implementations.

Verified Test Examples

The standalone AlgorithmsDataStructuresTest runner passed 23 of 23 checks with zero failures. Representative assertions verified that contact search for “ha” returned two matches, task search for “FLIGHT” returned two matches, and the upcoming-appointment filter returned three appointments with A1 first. Tests also covered empty collections, invalid terms, no-match searches, case insensitivity, and ordering. These are concrete checks of the new behavior rather than a generic claim that the enhancement works.

Reflection and Outcomes

This work reinforced that data structures should be selected for access patterns, not novelty. HashMap is appropriate for direct IDs; lists, traversal, and comparators are appropriate for flexible queries on a modest dataset. Outcome 3 is demonstrated by the algorithms, complexity analysis, and assertions. Outcomes 2 and 4 are supported by the explanation of trade-offs and use of standard Java collection tools. The test runner and unmodifiable results also contribute evidence of quality and defensive design.

03

Databases

SQLite persistence, JDBC repositories, schema constraints, indexes, and prepared statements.

Read the enhancement narrative ＋

Artifact and Rationale

The third enhancement extends the same CS-320-derived application from temporary in-memory storage to persistent SQLite storage. I selected this change because records should survive the lifetime of a single application process and because it demonstrates how an existing software design can evolve without discarding earlier architectural work.

Implementation

DatabaseManager initializes the schema and manages connections. Separate JDBC repositories handle Contact, Task, and Appointment records, with primary keys, constraints, indexes, and parameterized SQL. The services continue to depend on Repository<T>, so switching from InMemoryRepository to a SQLite repository does not require rewriting business logic. Prepared statements reduce SQL-injection risk for values, while schema constraints reinforce application-level validation. Try-with-resources closes JDBC resources.

Verified Integration Evidence

The standalone SqliteIntegrationTest runner completed 17 of 17 checks successfully during the final local run. The suite exercises CRUD operations, persistence across reopened connections, constraints, and index behavior. The test is designed to reopen the same database file to check that stored records survive connection closure; that is evidence of persistence across sessions, though it is not a separately observed full application restart. Together with the 23 passing algorithm checks, the project has 40 passing standalone checks. These are not JUnit test counts.

Reflection and Outcomes

The main lesson was that database integration is an architectural decision, not merely a new place to store records. Reusing the repository abstraction made the change smaller and easier to reason about. Outcome 4 is demonstrated by JDBC and SQLite implementation; Outcome 5 by prepared statements, validation, and constraints; and Outcome 3 by the trade-offs between in-memory lookup and database-backed access. The code review, test evidence, and narrative support technical communication and collaborative review.
